# プロンプト管理方針

このプロジェクトでは `/home/mizuki2/dev/prompt_management_policy.yaml` の方針に合わせ、プロンプトを「YAMLの素材バンドル」と「コード側の安全な組み立て」に分ける。

## 採用形式

- 正本: `src/game/prompts/materials.yaml`
- 形式: `material_bundle`
- 対象: 役職戦略、フェーズ別指示、共通情報境界、出力JSON契約、ラウンド要約、ペルソナ、昼の状況別話法、日本語話法
- コード側: YAMLの読み込み、スキーマ検証、実行時情報の選別、秘密情報の露出制御、最終プロンプトの組み立て

## 責務分担

YAMLは、LLMに渡す静的な文言とレビュー対象のルールを持つ。長い説明や戦略文は自然文のまま置き、短いルールや選択肢は配列として管理する。

アプリケーションコードは、ゲーム状態に応じた素材選択とデータ露出制御を担当する。プレイヤー名、フェーズ、履歴、役職別の非公開情報、合法ターゲットは実行時に組み立てる。

## 発言対象の設計

昼議論の `suspects` / `trusts` は、現在応答でき、投票対象にもなり得る生存者だけを対象にする。墓地のプレイヤーは死亡、過去の発言、投票履歴、占い結果などの歴史情報として参照できるが、現在の疑い先・信頼先・圧力先・処刑候補にはしない。

この制約はプロンプト文言だけでなく、コード側でも `legalPlayers` として生存者のみを渡し、返却メタデータを同じ候補リストで正規化する。これにより、LLMが墓地のIDを `suspects` に返しても公開履歴や要約には載せない。

## 昼議論の巡回設計

昼議論は各ラウンド2巡で回す。1巡目は読み、役職主張の判断、質問を場に出すための発言にし、2巡目はその日すでに自分へ向いた質問や疑いに返答してから投票前の読みを更新する。

この設計により、発言順が早いプレイヤーも後続の疑いや質問に返答できる。各発言は短いまま保ち、長文の独演ではなく、短い応答の往復で人狼らしい弁明、反論、読み直しを発生させる。

## データ露出

- `public`: 公開履歴、生存者一覧、公開フェーズ情報
- `confidential`: 自分の役職、個人メモリ、役職ごとに許可された非公開情報
- `secret` / `forbidden`: APIキー、環境変数、許可されていない内部状態。プロンプトに含めない

役職別の秘密情報は `buildPromptContext` の allowlist で制御する。たとえば人狼は仲間だけ、占い師は自分の占い結果だけ、魔女は薬と襲撃対象だけを受け取る。

## 変更手順

1. 文言を変える場合は `materials.yaml` を編集する。
2. 出力JSON契約や意味が変わる場合は `version` を上げる。
3. 新しい役職、フェーズ、ペルソナ、状況キーを追加する場合は `materials.ts` の検証リストも更新する。
4. 実行時の秘密情報を追加する場合は、YAMLではなくコード側の露出制御とテストを先に追加する。
5. `pnpm test` と `pnpm build` を実行する。

## 検証

`src/game/prompts/materials.ts` はYAMLを実パーサで読み込み、必須フィールド、役職・フェーズ・ペルソナの網羅、出力契約、感度分類、未宣言プレースホルダを検証する。代表的なレンダリングと秘密情報の露出制御は `tests/prompts.test.ts` で確認する。
